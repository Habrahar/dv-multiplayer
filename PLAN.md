# План: личные профили игроков в мультиплеере

Ветка: `feature/per-player-money`. Апстрим — `upstream` (AMacro), оригинал — `insprill`.

Модель, к которой идём: **мир общий, прогресс личный.** Предметы физически одни на всех,
деньги/лицензии/джобы у каждого свои.

---

## Сделано

### Личные кошельки (проверено в игре: у хоста 16k, у нового игрока 0)

| Что | Где |
|---|---|
| Кошелёк: `Money`, `AddMoney`, `RemoveMoney`, `SetMoney`, `IsHost` | `Multiplayer/Networking/Data/ServerPlayer.cs`, регион `#region Wallet` |
| Стартовые деньги новичка (1000) | `ServerPlayer.STARTING_MONEY`, применяется в `ClientboundSaveGameDataPacket.cs` |
| Адресная отправка баланса (была броадкастом) | `NetworkServer.SendMoney(ServerPlayer)` |
| Списание: удаление вагона, ререйл, рабочий поезд, лицензии | `NetworkServer.cs`, 4 места, ищи `player.RemoveMoney` |
| Списание: внесение наличных в кассу | `NetworkedCashRegisterWithModules.Server_ProcessCashRegisterAction` |
| Персист баланса по GUID | `NetworkedSaveGameManager.Server_UpdateInternalData` |

**Ключевое решение:** кошелёк хоста — это его собственный `Inventory` (им владеет
ванильный сейв), у остальных отдельное поле, персист в JObject по GUID. Второго
источника правды нет. Хост исключён из `Server_UpdateInternalData` — так было и до нас.

**Долг:** `CashRegisterBasePatch.AddCash` ищет получателя через `GetClosestPlayer` — см.
«Известные баги», Б1.

### Ответ на отклонённую покупку лицензии (в игре не проверено)

| Что | Где |
|---|---|
| Ответ RPC на все 3 ветки отказа + на успех | `NetworkServer.OnServerboundLicensePurchaseRequestPacket`, `DenyLicensePurchase` |
| Тип ответа (`UnknownLicense`, `OutstandingDebts`, `InsufficientFunds`) | `Multiplayer/Networking/Data/RPCs/LicensePurchaseResponse.cs` |
| `TicketId` в запросе | `ServerboundLicensePurchaseRequestPacket`, `NetworkClient.SendLicensePurchaseRequest` |
| Экран держится до ответа, показывает причину, таймаут | `Multiplayer/Patches/SaveGame/CareerManagerLicensePayingScreenPatch.cs` |
| Строки отказа | `Locale.cs` (`CAREER_MANAGER__LICENSE_REFUSED*`), `locale.csv` |

Взят готовый механизм тикетов (`RpcManager`/`RpcTicket`) — тот же, на котором работает
вызов рабочего поезда по рации. Свой велосипед не нужен.

**Ключевое решение:** отказ несёт обратно авторитетный баланс. Касса карьер-менеджера
(`CashRegisterCareerManager`) в моде не синхронизируется вообще — деньги уходят из
кошелька локально ещё при внесении. Без ресинка терминал бы починили, а игрок остался
с заниженным балансом до следующего денежного события. Это тот же рассинхрон в профиль.

Попутно вернул `return false` при неудачном локальном `Buy()`. Ванилла в этом случае
делает только `break`, так что `return true` заставлял вызвать `Buy()` дважды и звук
«не хватает денег» играл два раза. Причиной залипания эта строка не была.

**Проверено в игре (0.1.15.2):** кошельки у всех свои, терминал у каждого свой. Отказ от
сервера ещё не проверен — случай «внёс $40, не хватило» до сервера не доходит: ванильный
`Buy()` отказывает локально. Нужен долг у хоста (см. ниже).

### Чужая покупка больше не рисует по твоему терминалу (в игре не проверено)

`NetworkClient.OnClientboundLicenseAcquiredPacket` дёргал `PopulateTextsFromIndex` на
**всех** `CareerManagerLicensesScreen` в сцене. Лицензии общие, поэтому пакет приходит
всем, и список лицензий перерисовывался поверх того экрана, который игрок в этот момент
читал: уходя, `Disable()` тексты стирает, а возвращаясь, `Activate()` их сам заполнит.
Отсюда «зависший» терминал у второго игрока при чужой покупке.

Теперь обновляется только экран, который реально открыт — сверяемся с
`DisplayScreenSwitcher.CurrentScreen`. Покупателю обновление по-прежнему приходит: он на
этом экране и стоит.

### Награда за джоб — тому, кто сдал (в игре не проверено)

| Что | Где |
|---|---|
| Начисление в кошелёк сдавшего вместо печати купюр | `Multiplayer/Patches/Jobs/MoneyPrinterJobValidatorPatch.cs` |
| Проброс «кто сдал» через `ValidateJob` | `JobValidator_Patch.JobSubmitter` / `SetJobSubmitter` |
| Точка, где сервер знает отправителя | `NetworkServer.OnServerboundJobValidateRequestPacket`, ветка `JobBooklet` |

Ванилла платит физическими купюрами: `ValidateJob` → `moneyPrinter.PrintPayment(job)` →
через 3 с спавнит `Banknotes` у валидатора, игрок подбирает кошельком. Мод этот путь не
трогал вообще — ни одного упоминания `MoneyPrinter`/`PrintPayment`/`GetWageForTheJob`.

Беда в том, что бланк клиента валидирует **сервер**, поэтому купюры печатались в мире
хоста, и клиент их не видел — предметы не синхронизируются. Проверено вживую: игрок вернул
себе $40 из кассы, второй игрок этих купюр не видел.

**Ключевое решение:** печать купюр отключена (в мультиплеере; одиночная игра нетронута,
`IsSinglePlayer`), деньги идут прямо в кошелёк сдавшего. Физический путь честно заработает
только после оживления синхронизации предметов (п.1) — до тех пор показать купюры клиенту
нечем. Ритуал «забери наличку из диспенсера» при этом теряется, включая хоста.

### Личные лицензии (в игре не проверено)

| Что | Где |
|---|---|
| Наборы лицензий игрока + стартовый набор | `ServerPlayer.cs`, регион `#region Licenses` |
| Покупка клиента пишется игроку, а не хосту | `NetworkServer.OnServerboundLicensePurchaseRequestPacket` |
| Адресная выдача (была броадкастом) | `NetworkServer.SendLicense(ServerPlayer, id, isJob)` |
| Прогресс хоста больше не рассылается | `NetworkedSaveGameManager` — подписки на `LicenseAcquired`/`JobLicenseAcquired` убраны |
| Персист по GUID | `NetworkedSaveGameManager.Server_UpdateInternalData` |
| Личные лицензии при входе | `ClientboundSaveGameDataPacket` |

**Что было сломано:** сервер на покупку клиента звал `LicenseManager.Instance.Acquire*`, а это
**менеджер хоста**. Хост получал лицензию, которую не покупал, и событие рассылало её всем.
Плюс `ClientboundSaveGameDataPacket` отдавал каждому входящему лицензии хоста из сейва.

**Стартовый набор — не наш выбор, а требование игры.** `LicenseManager.LoadData` после
загрузки сама принудительно выдаёт `TrainDriver`, `DE2` и `FreightHaul`, если их нет, и
ругается в лог. Поэтому отдаём набор явно: `ServerPlayer.StartingGeneralLicenses` читает
`LicenseManager.TutorialGeneralLicenses`, а не хардкодит. К слову, ванилла при «скипнутом
туторе» даёт **$2000**, а у нас `STARTING_MONEY = 1000` — если захочешь сравнять, это здесь.

Клиент лицензии больше нигде для геймплея не спрашивает — сервер их не валидирует, проверено.

**Гаражи оставлены общими.** Их открывает физический замок в мире (`OnPadlockUnlocked` →
`UnlockGarage`), а не покупка, — на сервере нет момента, к которому привязать владельца.
Сделать их личными без серверного пакета «я открыл замок» нельзя, а это уже про рабочие
поезда, которые отложены.

### Личные джобы (в игре не проверено)

| Что | Где |
|---|---|
| Владелец джоба (Guid) + его id для провода | `NetworkedJob.OwnedBy` / `OwnerId` |
| Владелец в данных джоба | `JobData.OwnerId`, `JobUpdateStruct.OwnerId` |
| Выдача джоба по игроку, а не по хосту | `NetworkServer.Server_TakeJob` |
| Хост как владелец своих джобов | `JobValidator_Patch.ProcessJobOverview_Postfix` |
| Лицензии/слоты игрока | `ServerPlayer.IsLicensedForJob`, `AllowedConcurrentJobs`, `TakenJobCount` |
| Берёт джоб только владелец | `NetworkedStationController.HandleJobStateChange`, `AddJob` |
| Освобождение слота | `NetworkedJob.ReleaseFromOwner` |

**Что было сломано:** сервер звал ванильный `ProcessJobOverview` — тот судит **хоста**
(его лицензии, его слоты, его долги), кладёт джоб в `currentJobs` хоста и печатает бланк на
принтере хоста. А на клиентах `HandleJobStateChange` и `AddJob` звали `TakeJob(true)`
**у всех подряд** — поэтому джоб появлялся у каждого.

**Ключевое решение:** хост по-прежнему держит все джобы в своём `JobsManager` — это не
косметика, а движок: `JobsManager.Update` тикает задачи только тех джобов, что лежат в
`currentJobs`, а `CompleteTheJob` кидает исключение для чужих. Поэтому владение отдельно
(`OwnedBy`), а хранение общее. Клиенты же берут джоб только свой.

**Грабля, на которую наступил:** `TakeJob(job, takenViaLoadGame: true)` (нужен, чтобы не
будить долговой контроллер хоста за чужой джоб) **молча не помечает джоб dirty** — рассылка
бы не ушла вовсе. Отсюда явный `MarkStateDirty()`.

**Бумажки не требуют синка предметов.** Джоб-система сама их создаёт (`BookletCreator`) и
убивает (`DestroyJobOverview`) по job-пакетам — в том числе из рук. Это уже работало.

**Пути не колизятся** — генерация централизована: триггер по близости любого игрока
(`AnyPlayerSqrMag`), но джобы создаёт `StationController` хоста, один пул, а ванильный
`YardTracksOrganizer` резервирует пути между джобами. Не проверено вживую, но по устройству
двух джобов на один путь быть не должно.

**Долговой гейт для клиентов снят.** Ванилла проверяла `IsPlayerAllowedToTakeJob()` — долги
хоста. Для личного прогресса это неверно, поэтому в `Server_TakeJob` его нет. Пока личных
долгов не будет, у клиентов гейта по долгам нет вообще.

## Дальше по порядку

### 1. Синхронизация предметов

Цель: **один экземпляр предмета на мир.** Взял со стола — у остальных он со стола пропал.
Никаких «у каждого своя копия лопаты».

#### Главное: архитектура уже есть и она правильная

Это не проект с нуля. Модель заложена **серверно-авторитетная**, и она ровно та, что нужна:

| Кусок | Где | Состояние |
|---|---|---|
| Каждый предмет — `NetworkedItem` | `ItemBasePatch` — постфикс на `ItemBase.Awake` | Работает |
| Клиент прячет свои локальные предметы мира в пул при входе | `NetworkedItemManager.CacheWorldItems`, зовётся из `NetworkClient.cs:310` | Работает |
| Сервер шлёт авторитетный набор: `Create` / `Destroy` / состояние | `ProcessChanged` → `SendItemsChangePacket` | Работает |
| Клиент создаёт/убирает предмет по снапшоту, с пулом префабов | `ProcessReceivedAsClient`, `CreateItem`, `SendToCache`, `BuildPrefabLookup` | Работает |
| Состояния: `Dropped`/`Thrown`/`InHand`/`InInventory`/`Attached` | `NetworkedItem.ItemState` | Работает |
| Владение + проверка дистанции | `ValidatePlayerAction` | Написано, отключено |
| Раздача снапшотов по близости к игроку | `UpdatePlayerItemLists`, `MAX_DISTANCE_TO_ITEM = 100` | Работает |

**Выключено ровно две строки** — оба вызова `ReceiveSnapshots`:
`NetworkServer.cs:2137` и `NetworkClient.cs:1333`. Всё остальное живое.

#### Почему выключили — выяснено, и это меняет оценку риска

Коммит `b82d477 «Compatibility with B99»`, 24.11.2024. Прошлая версия плана писала «год не
работало, неизвестно что ломалось, большой риск». Посмотрел диф — там три вещи:

1. `GrabberRaycasterDV.SPHERE_CAST_MAX_DIST` → `RAYCAST_MAX_DIST` — переименование API игры.
   **Уже починено**, в коде новое имя.
2. `Server.PlayerDisconnect` — событие пропало, подписку закомментировали. `PlayerDisconnected`
   рядом кидает `NotImplementedException`. **Дыра: владение предметами при выходе игрока.**
3. `return;` в начале `CacheWorldItems` + оба `ReceiveSnapshots`.

То есть это была **не отмена по архитектурной причине, а заглушка на время миграции на B99**,
которую не доделали. Пункт 3 частично уже откатили: `41fabc5` убрал `return` из
`CacheWorldItems`, а `ReceiveSnapshots` не тронул.

#### Что происходит на самом деле — проверено в игре

Я предсказал по коду, что у клиента не должно остаться лежащих предметов: он же прячет их в
пул, а `Create` от сервера не приходит. **Предсказание неверное.** В игре наблюдается:

- предмет лежит на столе у обоих, каждый может взять — то есть **копия у каждого**;
- бросил на пол — второй игрок этого не видит, у него предмет там же, где лежал;
- повесил лампу — второй не видит;
- положил свои предметы — не видит.

Значит `CacheWorldItems` своей цели **не достигает**, и «один экземпляр на мир» сейчас нет.
Это одноразовый проход в момент входа (`NetworkClient.cs:310`), и он, судя по всему, либо
отрабатывает раньше, чем предметы мира успевают появиться, либо предметы возвращаются после
него. Диагностировать надо в игре: залогировать, сколько предметов проход реально спрятал.

**Вывод для проекта:** одноразовой уборки мало. Клиент не должен спавнить свои предметы мира
вообще — подавлять надо в момент появления (постфикс `ItemBase.Awake`, где предмет и так уже
становится `NetworkedItem`), пропуская только те, что создал сам сервер через `CreateItem`.
Одноразовый `CacheWorldItems` при таком раскладе становится не нужен.

#### Порядок работ

**Этап 1. Убрать дубли.** Сначала понять, почему `CacheWorldItems` не срабатывает (лог: сколько
предметов спрятал). Затем перевести подавление локальных предметов из одноразового прохода в
постоянное — на `ItemBase.Awake` у клиента. Без этого включать снапшоты бессмысленно: к
серверным предметам просто добавятся локальные, дублей станет больше, а не меньше.

**Этап 2. Включить снапшоты и посмотреть.**
Раскомментировать два вызова `ReceiveSnapshots`. Заглушку `return true` в
`ValidatePlayerAction` **не трогать пока** — сначала убедиться, что поток живой и предметы
появляются у клиента там же, где у хоста. Отдельно доделать B99-переезд:
`SPHERE_CAST_MAX_DIST`→`RAYCAST_MAX_DIST` уже сделан, `PlayerDisconnected` — нет (Б10).

**Этап 3. Снять заглушку валидации и сразу починить Б5 и Б6.**
Порознь их включать нельзя:
- **Б5** — проверка дистанции до замёрзшего transform отвергнет законное перекладывание из
  рук в инвентарь. Дистанцию проверять только при свежем подборе (`currentOwner == null`).
- **Б6** — `snapshot.Player` берётся с провода. `snapshot.Player = player.PlayerId;` в начале
  `ProcessReceivedAsHost`, до всякой обработки.

**Этап 4. Выход игрока (Б10).** `PlayerDisconnected` кидает `NotImplementedException`, а
подписки нет вообще. Решить: предметы в руках вышедшего падают на землю (`ClearOwnedItems` +
`Dropped` снапшот всем) или исчезают вместе с ним. Падать на землю честнее — иначе предмет
пропадёт из мира навсегда.

**Этап 5. Lost & Found — у каждого свой.**
В сторожке есть кнопка возврата потерянных предметов. Ванилла: `StorageAccessPointLostAndFound`
→ `StorageController.RequestLostAndFoundItemActivation()`, хранилище — `StorageLostAndFound`,
наполняется через `AddItemToLostAndFound` / `MoveItemsFromWorldToLostAndFound`.

Мод это **не трогает вообще**: `StorageControllerPatch` целиком закомментирован (там был
только отладочный лог стектрейсов).

Сейчас `StorageController` — синглтон на каждом клиенте, то есть Lost & Found у каждого свой
и локальный. Как только предметы станут общими, вопрос «чьи потерянные» станет настоящим:
нажал кнопку — вернуться должны **твои**, а не всё, что мир потерял.

Заготовка есть: `ServerPlayer.Storage` (`StorageBase`) объявлен и не используется — как
`OwnedBy` у джобов. Туда и складывать. Кнопка → серверный запрос → сервер возвращает предметы
этого игрока.

Тут же всплывёт вопрос владения: предмет, который ты никогда не брал, но который потерялся
в мире — чей он? Скорее всего Lost & Found делится на «мои потерянные» (я держал, `OwnedBy`)
и «ничьи из мира» (общие, возвращаются кому угодно).

**Этап 6. «Вижу предмет в чужой руке».** Сейчас взятый предмет просто гасится
(`gameObject.SetActive(false)`, `NetworkedItem.cs:622`) — «со стола пропал» этим и достигается,
а вот в руке его не видно. В коде стоит `//todo add to player model's hand`. Нужна точка
крепления на модели игрока и обновление позиции предмета по руке владельца.

#### VR и ПК

Разницы для синхронизации быть не должно: она **по состоянию** (`InHand`/`Dropped`/…), а не
по механике захвата. VR-игрок хватает иначе, но снапшот выходит тот же. `ServerPlayer.IsVR`
уже есть. Разница вылезет только на этапе 6: точка крепления в руке у VR-модели своя.

#### Чего это НЕ чинит

Бумажки джобов синхронизацией предметов **не заведуются** — джоб-система создаёт и уничтожает
их сама, по job-пакетам (см. «Личные джобы»). Они уже работают правильно и трогать их не надо.
Синхронизация нужна для остального: лопаты, фонари, маслёнки, банкноты, бумажки лицензий (Б3).

#### Идея: бланк и есть владение (твоя, 16.07)

«Не париться с синхронизацией джобов, а синхронизировать предметы: кто вставил — того и
джоб, кто подобрал — того и бланк.»

**Идея хорошая, и она снимает целый класс проблем.** Сейчас владение джобом — отдельная
бухгалтерия (`OwnedBy`/`OwnerId`, наборы на `ServerPlayer`, проброс владельца в двух
структурах пакетов), которая живёт **параллельно** физическому бланку и может с ним
разъехаться. Уже разъезжалась: без бланка не уходил его NetId, и клиент решал, что ему
отказали, хотя джоб он получил.

Если предметы синхронизированы честно, бланк **сам** становится токеном владения: он один на
мир, лежит у кого-то в руках или в кармане, и «чей джоб» — это просто «у кого бланк».
Отдельное поле владельца тогда нужно только серверу для проверок, а не как источник правды.

Что это даёт помимо простоты:
- **Передача джоба** появляется бесплатно: отдал бланк — отдал джоб.
- Пропадает рассинхрон «джоб мой, а бланка нет» — он физически невозможен.
- Не нужен `OwnerId` в `JobData` и `JobUpdateStruct`.

Чего не снимает: сервер всё равно должен судить **по игроку** (его лицензии, его слоты) в
момент вставки бланка, и всё равно должен знать, кому платить за сдачу. То есть `OwnedBy`
остаётся, но перестаёт быть тем, что клиент выясняет по проводу.

**Порядок от этого не меняется:** синхронизация предметов всё равно первая. Переводить джобы
на «бланк = владение» имеет смысл только после неё — тогда и посмотреть, что из нынешней
бухгалтерии можно выкинуть.

### 3. Джобы: доделать

**Ровно та же болезнь, что была у лицензий, и теперь она вылезла наружу.** Клиентский
префикс `ProcessJobOverview` возвращает `false` и шлёт запрос, а сервер зовёт ванильный
`ProcessJobOverview` — **в игре хоста**. Ванилла там проверяет три вещи, и все три хостовы:

- `LicenseManager.Instance.IsLicensedForJob(...)` — лицензии хоста
- `JobsManager.Instance.currentJobs.Count >= GetNumberOfAllowedConcurrentJobs()` — слоты хоста
- `CareerManagerDebtController.Instance.IsPlayerAllowedToTakeJob()` — долги хоста

И `TakeJobFromStation` кладёт джоб в `currentJobs` **хоста**.

Пока лицензии были общими, это совпадало и не было видно. Теперь противоречие прямое:
клиент купил лицензию, которой нет у хоста, — джоб не возьмёт; лицензии нет, а у хоста есть —
возьмёт. Лимит одновременных джобов общий на всех.

`NetworkedJob.OwnedBy` объявлен и **нигде не используется** — мёртвая заглушка под это.
Джобы рассылаются броадкастом (`SendJobsCreatePacket`/`SendJobsUpdatePacket` → `SendPacketToAll`).

Лечится тем же приёмом, что лицензии: не пускать чужое действие через синглтоны хоста.
Нужны наборы взятых джобов на `ServerPlayer` и проверки против **его** лицензий/слотов/долгов,
а не хостовых. `OwnedBy` — готовое место для владельца.

Наработки в `upstream/feature/sync-jobs` — 14 коммитов, 1627 строк:
`StationPatch`, `StationJobGenerationRangePatch`, фиксы спавна бланков, синхронизация табличек.

**Не мержить целиком.** Ветка отстаёт от `beta` на 587 коммитов, пробный мерж дал
20 конфликтов из 29 файлов, и большинство не про джобы (`ServerBrowserPane`,
`NetworkedTrainCar`, `Settings`, `locale.csv`) — это год расхождения, а не полезная работа.
Переносить прицельно, кусками, поверх свежей `beta`.

Учесть: `sync-jobs` делает джобы **общими и согласованными**, а нужно — **личными**.
Фундамент оттуда полезен, часть логики придётся разворачивать.

Оплата за джоб уже адресная — идёт тому, кто сдал бланк (см. «Сделано»). Осталось владение
самим джобом: чей он, кто может его сдать.

### 4. Поезда: личные

**Отложено твоим решением.** Один блокер снят: долг за разбитый локомотив — на **владельце**,
том, кто вызвал (даже если разбил другой). Остаётся вопрос 2: что вообще значит «личный
поезд». Сюда же гаражи (Б4) — они часть этой темы, а не лицензий.

Самый запутанный пункт: долги, гаражи, владение вагонами.
`NetworkedCareerManagerDebtController` уже существует.

## Сборка

`dotnet build Multiplayer.sln -c Release` из корня. Версия в UMM подтверждает свою сборку.

Оговорки, на которые уходит время:

- Проект `MultiplayerAPI Tests` не собирается (нет namespace `MPAPI`) — это не наша поломка.
  Собирать `Multiplayer/Multiplayer.csproj` отдельно.
- `MultiplayerEditor.dll` и `UnityChan.dll` лежат в `<DvInstallDir>\Mods\Multiplayer`, а не в
  `Managed`. Основной репозиторий собирается только потому, что они уже осели в его `bin/`.
  В свежем клоне/воркtree добавь `$(DvInstallDir)\Mods\Multiplayer\` в `ReferencePath`
  в своём `Directory.Build.targets`.
- `post-build.ps1` копирует мод в `<DvInstallDir>\Mods\Multiplayer` и делает
  `Releases\Multiplayer <ver>.zip` — теперь и из `dotnet` CLI тоже. Раньше только из Visual
  Studio: условия висели на `$(ConfigurationName)`, а это свойство VS, в CLI оно пустое и
  копирование молча не срабатывало. Заменено на стандартное `$(Configuration)`.
- Следствие: любая сборка перезаписывает мод в игре. Если игра запущена, DLL залочена и
  сборка упадёт — закрывай игру перед сборкой.
- Zip из `Releases/` ставится у другого человека через Unity Mod Manager. Версии должны
  совпадать у всех: мод сверяет их при входе, а формат пакетов мы меняем.
