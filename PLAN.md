# План: личные профили игроков в мультиплеере

Ветка: `feature/per-player-money`. Апстрим — `upstream` (AMacro), оригинал — `insprill`.

Модель, к которой идём: **мир общий, прогресс личный.** Предметы физически одни на всех,
деньги/лицензии/джобы у каждого свои.

---

## Сделано

### Личные кошельки (проверено в игре: у хоста 16k, у нового игрока 0)

| Что | Где |
|---|---|
| Кошелёк: `Money`, `AddMoney`, `RemoveMoney`, `SetMoney`, `IsHost` | `Multiplayer/Networking/Data/ServerPlayer.cs`, регион `#region Wallet` |
| Стартовые деньги новичка (1000) | `ServerPlayer.STARTING_MONEY`, применяется в `ClientboundSaveGameDataPacket.cs` |
| Адресная отправка баланса (была броадкастом) | `NetworkServer.SendMoney(ServerPlayer)` |
| Списание: удаление вагона, ререйл, рабочий поезд, лицензии | `NetworkServer.cs`, 4 места, ищи `player.RemoveMoney` |
| Списание: внесение наличных в кассу | `NetworkedCashRegisterWithModules.Server_ProcessCashRegisterAction` |
| Заработок: оплата джоба ближайшему к кассе игроку | `Multiplayer/Patches/World/CashRegisterBasePatch.cs`, префикс `AddCash` |
| Поиск ближайшего игрока | `DvExtensions.GetClosestPlayer` |
| Персист баланса по GUID | `NetworkedSaveGameManager.Server_UpdateInternalData` |

**Ключевое решение:** кошелёк хоста — это его собственный `Inventory` (им владеет
ванильный сейв), у остальных отдельное поле, персист в JObject по GUID. Второго
источника правды нет. Хост исключён из `Server_UpdateInternalData` — так было и до нас.

**Долг:** оплата джоба идёт по близости к кассе, а не по владельцу джоба. Хуже, чем
казалось: `GetClosestPlayer` вообще не ограничивает дистанцию, так что заплатить может
игроку за 20 км, если ближе никого нет. Фоллбэк на хоста срабатывает, только если
игроков нет совсем. Чинится вместе с джобами (см. п.4).

### Ответ на отклонённую покупку лицензии (в игре не проверено)

| Что | Где |
|---|---|
| Ответ RPC на все 3 ветки отказа + на успех | `NetworkServer.OnServerboundLicensePurchaseRequestPacket`, `DenyLicensePurchase` |
| Тип ответа (`UnknownLicense`, `OutstandingDebts`, `InsufficientFunds`) | `Multiplayer/Networking/Data/RPCs/LicensePurchaseResponse.cs` |
| `TicketId` в запросе | `ServerboundLicensePurchaseRequestPacket`, `NetworkClient.SendLicensePurchaseRequest` |
| Экран держится до ответа, показывает причину, таймаут | `Multiplayer/Patches/SaveGame/CareerManagerLicensePayingScreenPatch.cs` |
| Строки отказа | `Locale.cs` (`CAREER_MANAGER__LICENSE_REFUSED*`), `locale.csv` |

Взят готовый механизм тикетов (`RpcManager`/`RpcTicket`) — тот же, на котором работает
вызов рабочего поезда по рации. Свой велосипед не нужен.

**Ключевое решение:** отказ несёт обратно авторитетный баланс. Касса карьер-менеджера
(`CashRegisterCareerManager`) в моде не синхронизируется вообще — деньги уходят из
кошелька локально ещё при внесении. Без ресинка терминал бы починили, а игрок остался
с заниженным балансом до следующего денежного события. Это тот же рассинхрон в профиль.

Попутно вернул `return false` при неудачном локальном `Buy()`. Ванилла в этом случае
делает только `break`, так что `return true` заставлял вызвать `Buy()` дважды и звук
«не хватает денег» играл два раза. Причиной залипания эта строка не была.

## Дальше по порядку

### 1. Синхронизация предметов — сначала решить, включаем ли вообще

**Прошлая версия плана здесь врала.** Заглушка `return true;` в
`NetworkedItemManager.ValidatePlayerAction` (строка 316) — не то, что блокирует валидацию.
Метод недостижим целиком, снятие заглушки не изменит ничего в рантайме.

Почему: `ValidatePlayerAction` зовётся только из `ProcessReceivedAsHost` ← `ProcessReceived`
← очередь `ReceivedSnapshots`. Очередь наполняет единственный метод `ReceiveSnapshots`, и
у него ровно два вызова — **оба закомментированы**:

- `NetworkServer.cs:2137` — тело `OnCommonItemChangePacket` целиком в комментариях
- `NetworkClient.cs:1333` — то же на клиенте

Отключил AMacro 24.11.2024, коммит `b82d477 «Compatibility with B99»` — временная мера под
билд игры B99, так и осталась. Синхронизация предметов мертва в обе стороны: клиент шлёт
снапшоты — сервер выбрасывает; сервер шлёт — клиент выбрасывает. `ItemUpdateData` живёт в
6 файлах, `NetworkedItem` — обычный `IdMonoBehaviour` без автосинка, обходного пути нет.

Решение нужно до кода: включаем синхронизацию (большой риск — неизвестно, что именно
ломалось на B99, год не работало) или оставляем и идём дальше. Заготовка в
`upstream/feature/item-sync` — посмотреть до того, как писать своё.

**Два бага, которые всплывут в момент включения** (найдены чтением, не запуском):

- **Дистанция отвергнет законное действие.** При взятии предмет деактивируется
  (`NetworkedItem.cs:622`), его transform замерзает на месте подбора. Игрок отошёл на 100 м,
  переложил из рук в инвентарь → снапшот `InInventory` → дистанция до замёрзшего transform
  100 м > 4.5 м → отказ. Похоже, это и есть настоящая причина заглушки. Чинится проверкой
  дистанции только при свежем подборе (`currentOwner == null`).
- **`snapshot.Player` не сверяется с отправителем.** Валидация проверяет `player` (по
  аутентифицированному peer), а владение назначается по `snapshot.Player` — байту с провода
  (`ItemUpdateData.cs:115`). Эксплойт: уронить предмет, указав чужой id, — владение
  останется за атакующим, предмет залочен навсегда. Лечится строкой
  `snapshot.Player = player.PlayerId;` в начале `ProcessReceivedAsHost`.

### 3. Личные лицензии

Сейчас общие: хост покупает — получают все.

- `NetworkedSaveGameManager.Server_OnLicenseAcquired` / `Server_OnJobLicenseAcquired` /
  `Server_OnGarageUnlocked` — сейчас броадкастят
- `NetworkServer.SendLicense` / `SendGarage` — сделать адресными (как уже сделано с `SendMoney`)
- `ClientboundSaveGameDataPacket.cs` — сейчас отдаёт лицензии хоста
  (`data.GetStringArray(SaveGameKeys.Licenses_General)`), должен отдавать личные
- персист по GUID — туда же, где баланс
- стартовый набор: `StartingItemsController.Instance.AddStartingItems(...)` уже вызывается
  на каждом входе в `StartGameData_ServerSave.cs:125` — это источник правды «что даёт тутор»

Подводный камень: бумажки общие → взять может игрок без лицензии. Отказывать надо
в момент **применения**, не поднятия.

Ещё: клиент и сейчас не получает физическую бумажку. Ванилла печатает её через
`BookletCreator.CreateLicense` + `licensePrinter.Print()` прямо в экране, а патч это
пропускает — лицензия приезжает пакетом, бумажка ниоткуда. Само по себе не чинится:
предметы не синхронизируются (см. п.1).

### 4. Джобы: свои у каждого

Наработки в `upstream/feature/sync-jobs` — 14 коммитов, 1627 строк:
`StationPatch`, `StationJobGenerationRangePatch`, фиксы спавна бланков, синхронизация табличек.

**Не мержить целиком.** Ветка отстаёт от `beta` на 587 коммитов, пробный мерж дал
20 конфликтов из 29 файлов, и большинство не про джобы (`ServerBrowserPane`,
`NetworkedTrainCar`, `Settings`, `locale.csv`) — это год расхождения, а не полезная работа.
Переносить прицельно, кусками, поверх свежей `beta`.

Учесть: `sync-jobs` делает джобы **общими и согласованными**, а нужно — **личными**.
Фундамент оттуда полезен, часть логики придётся разворачивать.

Здесь же чинится оплата «по близости» из блока «Сделано».

## Сборка

`dotnet build Multiplayer.sln -c Release` из корня. Версия в UMM подтверждает свою сборку.

Оговорки, на которые уходит время:

- Проект `MultiplayerAPI Tests` не собирается (нет namespace `MPAPI`) — это не наша поломка.
  Собирать `Multiplayer/Multiplayer.csproj` отдельно.
- `MultiplayerEditor.dll` и `UnityChan.dll` лежат в `<DvInstallDir>\Mods\Multiplayer`, а не в
  `Managed`. Основной репозиторий собирается только потому, что они уже осели в его `bin/`.
  В свежем клоне/воркtree добавь `$(DvInstallDir)\Mods\Multiplayer\` в `ReferencePath`
  в своём `Directory.Build.targets`.
- `post-build.ps1` копирует мод в `<DvInstallDir>\Mods\Multiplayer` **только из Visual
  Studio**: условия завязаны на `$(ConfigurationName)`, а в сборке через `dotnet` CLI это
  свойство пустое и копирование молча не срабатывает. Из CLI ставить руками.
